# TestFlight setup runbook

Runs on the user's Mac, where Xcode and the login keychain are. The CI
pipeline it configures is `.github/workflows/testflight.yml`; the reference
documentation is `docs/TESTFLIGHT.md`. Read that if a step here is
ambiguous — this file is the sequence, that one is the detail.

## Handling key material

This procedure touches the user's Apple signing identity. Non-negotiable:

- **Never print** the contents of the `.p8`, the `.p12`, or their base64 to
  the transcript. Pipe them; don't `cat` them. If you need to confirm a file,
  check its size or its first line only (`head -1`).
- **Never place them inside the repo.** Keep them somewhere like
  `~/.appstoreconnect/`. If one is already in the working tree, stop and tell
  the user before doing anything else.
- **Pass secrets on stdin, not argv** — `gh secret set NAME < file`, not
  `--body "$VALUE"`. Values in argv are visible to `ps`.
- Delete any temporary base64 file when you're done.
- `local.xcconfig` holds a team ID and is gitignored. Never commit it.

## Step 0 — Read the config

Everything project-specific is in `ci/release.config`:

```sh
cat ci/release.config
```

Source it for the steps below (`XCODE_PROJECT`, `XCODE_SCHEME`, `PLATFORM`,
`TEAM_XCCONFIG`). If the file is missing, the pipeline was never installed —
run `Tools/install-testflight-pipeline.sh .` first.

Then run the preflight, which reports anything that would fail late:

```sh
Tools/install-testflight-pipeline.sh --check .
```

Fix everything it lists as blocking before going further. A placeholder bundle
ID is the user's call — ask which reverse-DNS ID they want and change it in
the Xcode project.

## Step 1 — Collect credentials

Two of these only the user can do, in a browser. Ask them to do these and
tell you when done; don't try to automate them.

1. **App Store Connect API key** — App Store Connect → Users and Access →
   Integrations → App Store Connect API → **+**, role **App Manager**. They
   need to save the `AuthKey_*.p8` (downloadable exactly once) and note the
   **Key ID** and **Issuer ID**.
2. **App record** — App Store Connect → Apps → **+** → New App. The platform
   must match `PLATFORM` in the config, and the bundle ID must match the
   target exactly. A watchOS-only app needs a watchOS record; this is not
   editable after creation.

You can do the rest:

```sh
security find-identity -v -p codesigning | grep "Apple Distribution"
```

The 10-character string in parentheses is the Team ID. If there's no such
identity, the user needs to create one: Xcode → Settings → Accounts → Manage
Certificates → **+** → Apple Distribution.

For the `.p12`, ask the user to export it from Keychain Access → **My
Certificates** → right-click the *Apple Distribution* row → Export. Tell them
explicitly to export the row with the **disclosure triangle** (which contains
the private key), not the bare certificate — exporting the wrong one produces
a `.p12` that codesign cannot use, and the failure only surfaces much later.

## Step 2 — Prove the signing chain locally

Do this before touching GitHub. It exercises the same commands CI runs, costs
no Actions minutes, and fails in a place where you can actually read the
error.

```sh
. ci/release.config
[ -n "$TEAM_XCCONFIG" ] && echo "DEVELOPMENT_TEAM = <team id>" > "$TEAM_XCCONFIG"

xcodebuild archive \
  -project "$XCODE_PROJECT" \
  -scheme "$XCODE_SCHEME" \
  -configuration Release \
  -destination "generic/platform=$PLATFORM" \
  -archivePath /tmp/tf-validate.xcarchive \
  -allowProvisioningUpdates \
  DEVELOPMENT_TEAM=<team id>
```

**Then check the archive actually contains an app.** This is the single most
valuable check in the runbook, because a wrong answer here produces a
successful-looking archive that fails at export:

```sh
ls -la /tmp/tf-validate.xcarchive/Products/Applications/
plutil -p /tmp/tf-validate.xcarchive/Info.plist | grep -A6 ApplicationProperties
```

`Products/Applications/` must contain the `.app`, and `ApplicationProperties`
must be present in the archive's `Info.plist`. If the directory is empty or
the key is missing, the target has `SKIP_INSTALL = YES`. That is correct only
for a target embedded in a containing app; for a standalone app set it to
`NO` in the project (and in `project.yml` too, if the project is generated by
XcodeGen, or the next `xcodegen generate` will undo it).

Now export, using the committed options with the team ID filled in:

```sh
cp ci/ExportOptions.plist /tmp/tf-export.plist
plutil -replace teamID -string "<team id>" /tmp/tf-export.plist

xcodebuild -exportArchive \
  -archivePath /tmp/tf-validate.xcarchive \
  -exportOptionsPlist /tmp/tf-export.plist \
  -exportPath /tmp/tf-export \
  -allowProvisioningUpdates \
  -authenticationKeyPath ~/.appstoreconnect/AuthKey_XXXX.p8 \
  -authenticationKeyID <key id> \
  -authenticationKeyIssuerID <issuer id>
```

An `.ipa` in `/tmp/tf-export` means the whole chain works: certificate,
profile, API key, entitlements, archive layout. Clean up afterwards
(`rm -rf /tmp/tf-validate.xcarchive /tmp/tf-export /tmp/tf-export.plist`) and
remove `$TEAM_XCCONFIG` if the user doesn't otherwise keep it.

If the user would rather ship this first build straight from the Mac, add
`plutil -replace destination -string upload` to a copy of the plist and
re-run `-exportArchive`. That uploads without involving CI at all.

## Step 3 — Set the GitHub secrets

Six per repo. `gh` must be authenticated (`gh auth status`).

```sh
REPO=<owner/name>
gh secret set APPLE_TEAM_ID            --repo "$REPO" < <(printf '%s' "<team id>")
gh secret set APPLE_DIST_CERT_PASSWORD --repo "$REPO"          # prompts, doesn't echo
gh secret set ASC_KEY_ID               --repo "$REPO" < <(printf '%s' "<key id>")
gh secret set ASC_ISSUER_ID            --repo "$REPO" < <(printf '%s' "<issuer id>")
gh secret set ASC_PRIVATE_KEY          --repo "$REPO" < ~/.appstoreconnect/AuthKey_XXXX.p8
base64 -i ~/.appstoreconnect/dist.p12 | gh secret set APPLE_DIST_CERT_P12 --repo "$REPO"
```

`ASC_PRIVATE_KEY` must be the whole `.p8` including its
`-----BEGIN PRIVATE KEY-----` / `-----END PRIVATE KEY-----` lines — reading
the file directly, as above, gets this right.

Verify with `gh secret list --repo "$REPO"`. It prints names and timestamps
only, never values.

GitHub has no account-level Actions secrets for personal accounts, so repeat
this per repo. The values are identical each time.

## Step 4 — Get the workflow onto the default branch

`workflow_dispatch` only appears in the Actions UI once the workflow file
exists on the repo's **default branch**. Check:

```sh
gh workflow list --repo "$REPO"
```

If `TestFlight` isn't listed, the workflow hasn't reached the default branch
yet. Merging is the user's call — ask how they want it done rather than
merging or force-pushing on your own.

## Step 5 — Run it

Dry run first. It archives, signs and exports the `.ipa` as an artefact but
skips the upload, so nothing is consumed in App Store Connect:

```sh
gh workflow run TestFlight --repo "$REPO" --ref <branch> -f dry_run=true
gh run watch --repo "$REPO"
```

On failure, pull the log for the failed step and diagnose from it:

```sh
gh run view --repo "$REPO" --log-failed
```

The troubleshooting table in `docs/TESTFLIGHT.md` maps the common errors to
causes. When it's green, re-run without `dry_run` for a real upload, or push
a `v*` tag.

Note for private repos: GitHub bills macOS runners at a **10× minute
multiplier**, so a 15-minute archive costs ~150 minutes of the monthly
allowance. If the user is doing many iterations, prefer the local validation
in Step 2 and keep CI runs for the real thing.
